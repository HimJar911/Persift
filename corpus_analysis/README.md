# Corpus open-coding — P1.2 → P1.3 bridge

**Status as of Jul 20, 2026: DONE.** All 3,074 fields in the 116-company real-form corpus (from P1.2's harvester) have been classified — either by deterministic clustering, by the founder reading every field individually with live-verified raw-HTML evidence, or by high-confidence auto-match against an already-confirmed category. `needs_review` is 0.

This directory is the tracked, permanent home for that work. It is derived analysis of `corpus/manifest.jsonl` (which stays gitignored, per `.gitignore`'s "generated data, not source" — the raw crawl can be regenerated by re-running the harvester; this directory's category taxonomy and decisions cannot be regenerated automatically and must not be lost).

## Why this exists (read this first)

P1.2's corpus harvester produced 767 crawled job postings. A first pass tried to auto-cluster identical/near-identical fields (matching `id`, `autocomplete`, normalized label text) to build a category system without hand-tuning against individual forms (see `FORM_ENGINE_DESIGN.md` §3.6a for why that discipline matters — it's the whole reason the harvester exists instead of just extending `filler_utils.js`). That clustering caught real duplicates but left ~2,100 fields unclustered residue.

The founder pushed back hard on treating "auto-clustered" as "done": (1) auto-clustering only catches *exact* string matches, so semantically-identical-but-differently-worded fields (e.g. "How did you hear about us?" vs "Where did you see or hear about this job?") never merge automatically — that's a judgment call, not a string match; (2) several early "confirmed" clusters turned out to be wrong when checked against raw HTML (see "The department_interest/location_preference correction" below) — pattern-matching without evidence produces confident-looking mistakes. The resolution: **read every residue field individually, verify against raw saved HTML whenever the label is ambiguous, and only classify with real confidence** — explicitly not semantic/LLM guessing dressed up as classification. Deterministic clustering only for the mechanical, unambiguous cases (exact id/label/autocomplete matches); human judgment for everything else, evidenced by HTML, worked through in small batches the founder reviewed live in chat before anything was written to a file.

## Pipeline (run in this order if you need to regenerate)

```
1. auto_cluster.py           reads ../scratchpad/oc_compact_full.json (or wherever
                              the compact corpus lives) → writes clusters.json
                              {clusters: [...], residue: [...]}. Five deterministic
                              rules, in priority order: id attribute match,
                              autocomplete spec match, normalized label match,
                              section-as-fallback-label match, known-pattern match
                              (currently: react-select required-input shim).

2. apply_decisions.py        applies the founder's confirm/reject/special calls
                              onto clusters.json's clusters → writes
                              cluster_decisions.json. Keyed by "rule::key" (NOT
                              bare key — several normalized keys are produced by
                              more than one rule, e.g. "email" via both id-rule
                              and label-rule as separate clusters).

3. residue_triage.py         reads clusters.json's residue + cluster_decisions.json
                              → splits residue into auto_match (>=0.60 word-overlap
                              against an already-CONFIRMED category's example
                              labels — mechanical, not semantic) vs needs_review
                              (everything else) → writes residue_triage.json.

4. apply_triage_decisions.py bulk-confirms every auto_match entry (all were
                              spot-checked for false positives, none found) →
                              writes triage_decisions.json.

5. manual_singleton_tags.py  hand-tags a handful of one-off fields found early in
                              the process, before the batch-review workflow below
                              existed → writes manual_singleton_tags.json.

6. batch{1..5}_decisions.py  the actual bulk of the work. Each batch: pull the
                              next chunk of needs_review fields, the founder and
                              the agent read them together in chat (small
                              sub-chunks, confirmed one at a time), raw HTML
                              pulled from corpus/pages/*.html.gz whenever a label
                              was ambiguous or a cluster's real nature was in
                              doubt, THEN the agreed calls get written into a
                              batchN_decisions.py script → batchN_decisions.json.
                              Merge into manual_field_index_tags.json after each
                              batch, regenerate clusters.json's residue list
                              (subtract every manual-tag + cluster-member key from
                              the full field set), re-run residue_triage.py, repeat.

7. correction_department_location.py   a mid-session correction, not a numbered
                              batch — see below. Also merged into
                              manual_field_index_tags.json.

Final state: manual_field_index_tags.json (975 entries) + manual_singleton_tags.json
(8 entries) + cluster_decisions.json (144 clusters: 98 confirmed / 43 rejected / 3
special) + triage_decisions.json (43 auto-matched) together cover all 3,074 fields.
```

**If you need to re-run this pipeline** (e.g. the corpus grows with more harvested companies), the residue-regeneration step (subtract all manual-tag keys + all cluster-member keys from the full field set) is NOT automated as a single script — it was run ad hoc in the terminal each time a batch merged. If you're picking this up, either extract that into a real script first, or be careful to replicate it exactly (see any `batchN` merge step in the git history / session transcript for the exact snippet).

## Field key format

Every decision is keyed by `(ci, fi)` — index into the compact corpus array, NOT by label text or job_id. `ci` = index into the top-level company array of `oc_compact_full.json`, `fi` = index into that company's `fields` array. This is deliberate: label text repeats across companies/fields in ways that are NOT the same question (see the department_interest correction below), and even `(job_id, field_id_hash)` isn't always stable enough — positional `(ci, fi)` against the exact compact-corpus snapshot in this directory (`oc_compact_full.json`) is the only fully unambiguous key. **If `oc_compact_full.json` is regenerated from a re-run of the harvester, all `(ci, fi)` references in every decision file become invalid** — the array order is not guaranteed stable across harvester runs. Treat `oc_compact_full.json` in this directory as the frozen snapshot these decisions apply to.

## The category system

~110+ categories now exist, essentially all traceable to a specific real field the founder read. Categories are NOT centrally listed anywhere yet as a single canonical enum — the closest thing is `sorted(set(cluster_decisions.json's confirm.values())) ∪ set(all category values across manual_field_index_tags.json + manual_singleton_tags.json)`. **Building that canonical list + picking final names (some are working names, e.g. `pep_disclosure`, `attention_check`) is upstream work for P1.4, not done here.**

Notable categories that are NOT simple "ask the user a fact" fields — flag these for P1.4's interpreter design, they need special handling, not just a label:
- **`other_followup`** — not a topic, a structural relationship (free-text follow-up to a preceding "Other" choice). Needs to resolve by finding the nearest preceding field, not by reading its own label.
- **honeypot fields** (found via `manual_field_index_tags.json`, e.g. Ogilvy's `edit-url`/`edit-send`) — must be actively SKIPPED, never filled, confirmed via raw HTML (`tabindex="-1" aria-hidden="true"`, label literally instructs "leave this field blank").
- **the react-select required-input shim** (`known_pattern::react_select_required_shim`, 75 fields, 53 companies) — a library-injected hidden validation input trailing custom comboboxes, not askable, resolves itself once the combobox it shims is filled. See `FORM_ENGINE_DESIGN.md` §7.
- **required field + no resolvable profile value → abort the whole application**, don't guess or submit incomplete. General resolution-layer rule, not specific to any one category. See `FORM_ENGINE_DESIGN.md` §7.

## The department_interest / location_preference correction (read before trusting any "obviously real" checkbox_group cluster)

Early in this session, checkbox groups sharing literal words like "Marketing," "Administration," "Boston, Massachusetts" across companies (Anduril, Cannondesign, D2L, Stripe, GoStudent, Ogilvy, OneAcreFund) got merged into `department_interest`/`location_preference` on pattern alone. When one of these (d2l's "No Department", `name="filter-group-1_4"`) got checked against raw HTML out of caution, it turned out to be a **job-board search/filter widget**, not an application-form field. Checking the rest of that cluster found the SAME word ("Marketing") meant four completely different fake things across four companies (job-board filter ×3 different widget libraries, Cookiebot cookie-consent banner ×1) plus one real Greenhouse field (omnicomhealth's actual "Department" question). 43 of 45 originally-merged fields were wrong.

**Lesson, now a standing practice for the rest of this session:** a checkbox_group cluster sharing option text across companies is NOT evidence those companies have "the same real question" — office/department/employment-type filter widgets are extremely common on job-listing pages and produce exactly this false-positive pattern. Always check raw HTML (`corpus/pages/{job_id}.html.gz`) for the actual wrapping `<label>`/`<legend>`/`aria-label`/class names before trusting a cross-company checkbox-group match, even (especially) when the pattern "looks obviously real."

## Two extraction bugs found and documented (for whoever next touches the harvester or `filler_utils.js`)

1. **Malformed empty-record artifact.** `field_id_hash == '709446a2'`, `tag: None`, every other attribute null — appeared identically 12x across 12 different companies' pages. A harvester bug (trailing bad record), not real DOM content. All 12 rejected by hash match in `batch2_decisions.py`.
2. **Placeholder-as-real-label gap.** Several forms (Anduril/Gem-platform, Workato, Trade Republic) put the actual question text in the DOM's `placeholder` attribute while `label` extracted empty — e.g. Trade Republic's `id="question_29988745003"` had `label: ""` but `placeholder: "Are you available and in Berlin between 15 July and 15 Oct 2026?"`. Confirmed via raw HTML on multiple independent examples, not a one-off. `enrichField()`/`collectFields()` (or their eventual P1.4 successor) should fall back to `placeholder` when `label` is empty, similar to the already-implemented `section`-as-fallback logic in `auto_cluster.py`'s clustering rule (which only helps the *analysis*, not the live extension — the live extraction code in `extension/filler_utils.js` doesn't have this fallback yet either).
