# `corpus/` — P1.2 raw harvest output

Generated by `pipeline/corpus_harvester.py`. **Not source — gitignored,
regenerable.** This directory is the raw crawl output; the analysis built on
top of it lives in `corpus_analysis/` (see that directory's own README, and
`decisions/0005-corpus-harvester-no-reuse.md` for why the harvester exists
and why it deliberately doesn't reuse `extension/filler_utils.js`).

## Contents

- **`manifest.jsonl`** — one line per crawled job posting: extraction status,
  the URL actually crawled (may differ from the stored `apply_url`, see
  below), and the full extracted field list for that posting's application
  form.
- **`pages/{job_id}.html.gz`** — gzipped raw HTML of the page actually
  extracted from, one per successfully-crawled job.

## Two harvest runs — read this before trusting a job count

1. **Original run, 2026-07-17.** Built and run same day, against **767
   Greenhouse jobs / 269 companies** — at the time, effectively all of what
   the `jobs` table held (an `is_intern_role()` title-drop-gate, removed
   2026-07-21 per [decisions/0002](../decisions/0002-intern-only-scope-removed.md),
   was silently discarding ~99% of real postings). 718 `ok` (28
   `no_form_found`, 14 `error`, 7 `likely_blocked`). This is the corpus
   `corpus_analysis/`'s full open-coding pass (clusters, 975 hand-tagged
   fields, the category system) was built against — see
   [decisions/0008](../decisions/0008-corpus-harvester-scale-and-scope-gap.md)
   for why that corpus predates the real job volume.
2. **Full-volume re-run, 2026-07-26 → 2026-07-28.** Same harvester
   (`HARVESTER_VERSION` now `1.3.0`, up from `1.0.0` — see below), same
   query shape but run to exhaustion against **all 20,837 Greenhouse jobs**
   in the (by then much larger, post-data-completeness-pass) `jobs` table —
   **267 distinct company tenants** confirmed from the manifest's crawled
   URLs. Result: **19,846 `ok` (95.2%)**, 768 `error` (3.7%), 107
   `likely_blocked` (0.5%), 106 `no_form_found` (0.5%), 10
   `apply_button_clicked_no_form`. Took ~2 real days of wall-clock time —
   not because the crawl itself is slow, but because of a long, genuinely
   rough fight with running Playwright/Chromium concurrency on a
   memory-constrained (~7.4GB RAM) dev laptop; see "Harvester resilience
   fixes" below and `STATE.md` for the full account. **`manifest.jsonl` and
   `corpus_crawl_state` now contain both runs' records together** (the
   harvester's `_fetch_target_jobs` query is `LEFT JOIN ... WHERE
   s.job_id IS NULL`, so the second run only added the ~20,070 jobs not
   already crawled — it did not re-crawl or invalidate the first run's 718
   `ok` records).

**Practical implication for anyone using this data next:** the
`corpus_analysis/` open-coding pass (categories, clusters, decision files)
was built against ONLY the first run's 767-job/269-company slice. The
second run's ~19,100 additional `ok` records are NOT yet run through that
pipeline — they're raw, uncategorized field data sitting in
`manifest.jsonl`/`corpus_crawl_state` waiting for someone to extend the
open-coding pass (or build the P1.3 replay harness) against the full
volume. Don't assume `corpus_analysis/`'s category coverage claims apply to
records outside the original 767.

## Harvester resilience fixes (2026-07-26, `HARVESTER_VERSION` 1.0.0 → 1.3.0)

Found and fixed while running the full-volume re-run — all in
`pipeline/corpus_harvester.py`, see inline comments at each fix site for
full detail:

- **Concurrency added** (`--concurrency` flag, default 1 = old sequential
  behavior). Runs N workers off a shared `asyncio.Queue`, one browser
  shared across all workers via `_get_or_relaunch_browser`.
- **A single worker's browser crash no longer kills the whole run.** Found
  live: `browser.new_page()` was called OUTSIDE `_crawl_one`'s try/except —
  under concurrency, one `TargetClosedError` propagated through
  `asyncio.gather` and killed all other in-flight workers (lost a run at
  ~2,855/19,412). Fixed: `new_page()` moved inside the try block, `_worker`
  itself wraps its whole per-job body in try/except, `gather(...,
  return_exceptions=True)` as defense in depth.
- **`new_page()` given an explicit timeout** (`asyncio.wait_for`). Found
  live on a memory-starved machine (~245MB free): `new_page()` has no
  timeout of its own and can hang indefinitely waiting for the OS/browser
  to allocate a process — 2 of 3 workers did exactly this in the field,
  silently, with no way to ever reach the except block.
- **Browser auto-relaunch**, both on death (`is_connected()` check) and on
  a schedule (`_BROWSER_RECYCLE_EVERY = 300` jobs) as a guard against
  Chromium/Playwright's known long-session memory creep, even with clean
  per-job page lifecycles.
- **`_BLOCK_STREAK_THRESHOLD` raised 8 → 20** — the old sequential-era
  threshold was too easily tripped by concurrent workers' interleaved,
  organically-clustered failures (e.g. one blocked tenant hit by several
  workers close together isn't the same signal as a real global block).

**Real root cause of the "2 days" wall-clock time, worth reading before
re-running at this volume again:** not the harvester's logic — a
memory-constrained dev laptop (~7.4GB total RAM) fighting for headroom
against VS Code (~1.5GB, 11 Electron processes), WSL2/Docker Desktop's
backing VM (~1GB, uncapped by default up to 8GB), and the browser workers
themselves. Concurrency 8 was the empirically-best tradeoff on this
machine (10 was measured *slower* than 8 — driver/OS overhead outweighing
added parallelism past that point). A `.wslconfig` cap
(`memory=1.5GB`) and a scheduled task
(`scripts/register_clear_standby_task.ps1` /
`scripts/clear_standby_memory.ps1`, calls `NtSetSystemInformation`
directly — same effect as RAMMap's "Empty Standby/Modified List" buttons,
no third-party binary) were added mid-run as mitigations. **If re-running
this harvester at full volume again, do it on a machine with real
headroom (4-8GB+ genuinely free) or a small cloud VM — this was a real,
avoidable time sink, not an inherent property of the crawl.**

## Scope and known limitations (read before trusting this data)

- **Greenhouse only.** Both runs sourced from `jobs WHERE ats='greenhouse'
  AND apply_url <> ''`.
- **A real share of `ok` records land on a generic job-search/listing page,
  not the specific job's real application form** — an upstream `apply_url`
  construction issue for some Greenhouse-embed postings, not a harvester
  bug. Not root-caused. Its practical effect on corpus trustworthiness was
  handled by `corpus_analysis/`'s hand-classification pass on the first run
  (which naturally excluded thin/generic-listing companies), not by fixing
  the root cause. Not yet handled for the second run's additional records.
- **Closed combobox `options` are mostly empty** — the value list only
  renders once a user opens the dropdown in a real browser; the harvester
  snapshots pre-fill state. Known limitation, not solved by this crawl.
- **Only 19 of 753 saved pages (2.5%) carry `schema.org` `JobPosting`
  structured data** with a real `jobLocation` field — checked 2026-07-22
  while investigating job-location reliability (measured on the first
  run's pages only). Real signal where present, far from sufficient
  coverage on its own.
